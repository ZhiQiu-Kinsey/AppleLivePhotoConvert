## 总体评估结论

当前最新改版的桌面端原型在**视觉降噪、沉浸感与排版质感**上实现了跨越式提升：
- 顶层全面吸收了 **Windows 11 Photos（微软照片）** 规范的 32px 极简工具条，相册缩放、画幅比例、排序、筛选与时间线分组高度聚合，彻底将屏幕空间归还给照片本身；
- 全面废除生硬的 Checkbox，严格统一使用现代 Fluent **ToggleSwitch** 与圆形相册勾选徽标；
- 空间瘦身完成了“待瘦身分析 ➔ 卷帘实时发丝级对比 ➔ 实时流速跳动 ➔ 空间回收庆贺”全闭环。

**综合评级：良好（Grade B+）**。底层架构稳固且零堆内存流式追加性能极强，但从严苛的人机工效与极端数据防灾视角审查，当前仍存在 **3 项 P0 级数据防灾安全盲点** 与 **4 项 P1 级人机交互阻断隐患**，必须在工程落地阶段执行闭环整改。

## 维度一：顶层紧凑工具条（Windows 11 Photos 规范）交互完整度审查

```
[ 相册实况胶卷 · 14 组照片 · 428.5 MB | 已选 14 项 ]    [☑ 选择] [▷] [⇅ ⌵] [T ⌵] [🝔 ⌵] [···]
```

### 1. 顶层各按钮的行为一致性与体验审查

1. **`[☑ 选择]` 按钮（严重的模式混淆与操作破坏）**：
   - **问题现象**：原型中点击 `[☑ 选择]`，代码判定 `allSelected ? selectAllPhotos(false) : selectAllPhotos(true)`，将其做成了“全选/反选开关”。
   - **工效隐患**：在 Windows 11 Photos 中，`[选择]` 是一个**模式切换器（Mode Switcher）**。当用户在海量相册中好不容易单选挑选了 8 张照片，若误点 `[☑ 选择]` 想退出多选，系统却因为检测到不是全选而粗暴执行了“全选全部照片”，瞬间抹杀用户此前辛苦挑选的心血！
   - **整改规范**：
     - 未进入选择模式时：卡片右上角默认隐藏勾选圈（仅鼠标 Hover 时浮现半透明微圈 `○`），保持相册纯净；
     - 点击 `[☑ 选择]`：按钮呈 Fluent 激活高亮态（进入多选模式），所有卡片常驻显示勾选徽标，右上角出现“完成/退出选择”；
     - “全选”操作严格限制在 `[···]` 菜单或 `Ctrl+A` 触发。

2. **`[▷]` 试播按钮（并发压力与视觉轰炸）**：
   - **问题现象**：点击 `[▷]` 执行 `playAllLivePhotos()`，通过一个计时器在页面上级联并发触发所有卡片微动回放。
   - **性能与工效隐患**：若相册有数千张照片，全局并发触发视频动画会导致 Avalonia / 浏览器瞬间创建数百个硬件解码管线，造成显存溢出（OOM）或严重掉帧卡死；同时全屏卡片像走马灯一样同时闪烁，产生严重视觉干扰。
   - **整改规范**：澄清 `[▷]` 为**沉浸式大图放映（Slideshow）**，从当前聚焦的照片弹窗进入全屏大图逐张播放；若需画廊微动，应严格限制为**“仅对当前视口（Viewport）内可见且已勾选的项目依次微动 1 次”**。

3. **`[T ⌵]` 筛选菜单（筛选视图与选中集合强行越界绑定）**：
   - **问题现象**：点击“仅待人工裁决”，原型代码执行了 `selectSuspiciousOnly()`——直接清空了用户的其他勾选，只勾选异常项！
   - **交互原则违背**：**“筛选（Filter）”控制的是视口可见性，“勾选（Selection）”控制的是操作对象**。用户想在画廊里“单看一眼异常照片长什么样”，系统却擅自把用户之前勾选的照片集合全清空了。
   - **整改规范**：筛选仅改变卡片的 `Visibility`（显示/隐藏）；用户切到“仅待裁决”视图时，原先已勾选的正常照片依然保留选中态；顶栏展示筛选指示芯片（如 `正在筛选: 仅待人工裁决 (1项) · [✕ 清除筛选]`）。

4. **`[🝔 ⌵]` 视图/缩放/时间线分组菜单（三维聚合与状态回显）**：
   - **优点**：顶层收拢符合设计哲学；
   - **体验盲点**：
     - **状态无回显**：按钮图标固定不变，用户无法从工具条一眼得知当前是“按月”还是“按日”，是“等高”还是“方形”；
     - **缺乏操作驻留**：每次点击一个选项后菜单立刻自动关闭（`dismiss`），若想同时调整“大图”和“按月份”，用户必须连续点击两次；
   - **整改规范**：工具条按钮增加动态 Tooltip（如 `视图与分组 (当前: 等高 · 中等 · 按拍摄日期)`），在 Avalonia 中支持子级 Flyout 菜单。

---

### 2. 时间线分组切换（日期/月份/年份/连续平铺）的视觉连贯性

1. **“连续平铺 (不分组)”断层问题**：
   - 原型中选择连续平铺时，仅隐藏了 `.timeline-header`，内部各卡片依然受制于外层的多个分块容器，导致各组之间的瀑布流列宽存在截断和空白间隙；
   - **整改规范**：选择“连续平铺”时，界面应将数据源绑定到单一扁平的 `VirtualizingWrapPanel` / `MasonryPanel`，实现真正浑然一体的连续流大画卷。
2. **海量数据下的视图重构与滚动锚定（Scroll-Anchor）**：
   - 真实相册（10,000 张）从“按日”切到“按年”，时间轴节点会剧烈折叠；
   - 必须在切换时锁定**当前屏幕视口中心照片（Center Anchor Item）**，切换后自动对齐至该照片所在的新年份卡片位置，禁止滚动条无规则跳跃或滚回顶部。

## 维度二：真实大相册导入与长流程生命周期审计

```
[首次启动空状态] ➔ 拖入 10,000 张相册 ➔ [骨架流式解析] ➔ [漏斗多维过滤] ➔ [异常项同屏裁决] ➔ [流式并发转换] ➔ [成果报告与一键定位]
```

### 1. 空状态引导与深层嵌套目录拖拽边界
* **现实场景**：用户拖入一个包含 50 个按年份命名的子目录，夹杂隐藏文件夹（如 `.DS_Store`、`Thumbs.db`、手机缩略图缓存等）；
* **防御要求**：文件扫描必须在后台异步线程执行，遇到软链接/硬链接（Junction / Symlink）严禁循环递归，遇到隐藏文件夹自动忽略；在拖拽至窗口边界时，必须提供全窗口的 Fluent 拖拽高亮遮罩响应。

### 2. 扫描漏斗条过滤的可见性与可解释性
* **体验割裂点**：顶部漏斗条 `已安全过滤非实况: 2,426 项 ▼`，悬停仅展示统计数字（单张普通照片 2,100 项、普通长视频 310 项…）；
* **潜在风险**：若某张实况照片配套的视频被用户截取为 31 秒（超过默认的 30s 门限），被系统判定为“普通长视频”而过滤掉，用户在当前 UI 没有任何渠道查阅到底是哪张文件被过滤，形成“信息黑盒”；
* **整改规范**：漏斗浮窗增加 `[检视已过滤明细清单]` 链接，支持以轻量列表查看被过滤文件路径，并提供“手动将其作为实况照片载入”的通道。

### 3. 待定异常项的人工裁决（双屏同帧比对与反悔撤销）
* **体验隐患 1：信息盲区导致无法决策**：
  - 目前异常卡片仅显示时差 4.25 秒和一个 `[人工确认配对]` 按钮；
  - 但摄影师判断两者是否同属一张实况照片，唯一依据是**看原图画面与视频首帧是不是同一瞬间的场景**！缺少双屏画面比对，盲目点击纯属碰运气。
* **体验隐患 2：缺少反悔与解除机制**：
  - 点击人工放行后，按钮直接 `disabled`，无法撤销；且界面缺少“解除错误配对（拆散）”或“手动重新关联另一视频”的操作。
* **整改规范**：
  - 点击异常项弹出**【双屏同帧比对检视弹窗】**：左侧展示静态照片高清图，右侧展示视频首帧播放器，正下方标注时差（如 `+4.25s`）与机型；
  - 提供三向决策：`[✓ 确认属于同一实况 (强制配对)]`、`[✕ 并非同一实况 (拆分处理)]`、`[🔗 手动关联其他视频...]`；
  - 放行后允许用户随时撤回重新判定。

### 4. 批量转换长流程：微观状态与宏观感知
* **卡片微观状态**：转换进行时，不能仅依赖底部单一的总进度条，画廊卡片自身必须联动状态：排队中（半透明）➔ 正在转换（旋转蓝环 + 实时百分比）➔ 成功（翡翠绿勾）➔ 失败（亮红框可点击看报错）；
* **系统通知与后台驻留**：10,000 张转换耗时较长，软件应支持最小化托盘后台运行；全部完成后发送 Windows 原生系统 Toast 通知并播放完成音效。

## 维度三：数据资产防灾与破坏性操作边界审计

这是作为 Safety Auditor 最为核心的审查项。**照片是用户不可再生的珍贵记忆，系统必须具备银行级防灾边界！**

### 1. 致命缺陷：并发循环内即时删除原片破坏整体事务性 (SEC-01)
* **源码漏洞定位**：
  在 `LivePhotoConvert.Core/Services/MotionPhotoMerger.cs` 第 121 行：
  ```csharp
  await MergeOneAsync(pair, outputBaseName, options, tempDirectory, token);
  Interlocked.Increment(ref succeeded);
  var cleanup = cleaner.Clean([pair.PhotoPath, pair.VideoPath]); // 致命隐患: 单张完成立刻删原片!
  ```
* **极端灾难推演**：
  用户处理 500 张照片，前面 50 张转换成功并在循环内立即物理删除了原片；跑到第 51 张时，突然停电、或者磁盘写满（Disk Full）、或者用户发现配置错误强行取消。
  **此时前 50 张原片已经被彻底物理粉碎，无法撤回，破坏了批次事务的完整性！**
* **安全防线铁律**：
  1. **禁止循环内物理删除**：批次运行期间，成功项仅记入缓存清单，严禁在 `Parallel.ForEachAsync` 内部调用 `File.Delete()`；
  2. **事务延后与二次确认**：只有在全量批次 100% 成功、校验通过且用户在成果报告页最终确认后，方可批量执行清理；
  3. **授权记忆自动清除（One-time Ephemeral Consent）**：任务结束或重新打开文件夹后，源文件处理下拉菜单**强制自动回跳至“保留原始文件”**，防止下一次任务被误伤；
  4. **回收站优先**：删除操作首选调用 `RecycleBin.Send()`（Windows 回收站兜底），物理粉碎仅作为带极强警告的次选。

---

### 2. 致命缺陷：空间瘦身就地覆盖缺少阻断式二次确认 (SEC-02)
* **问题现象**：
  在原型瘦身界面中，“就地覆盖原照片 (破坏性替换)”仅仅是一个普通的琥珀色 ToggleSwitch。用户随手一拨，界面仅隐藏了导出目录，**中途无任何弹窗警示、无需输入确认词，点击“开始执行相册瘦身”即直接发起物理覆盖写入！**
* **极端灾难推演**：
  瘦身操作本质是**永久剥离 Live Photo 中的视频流**。用户若误以为瘦身是“无损压缩视频”，随手一按就地覆盖，全家相册的动态视频流将全部被永久抹除，再也无法还原回实况照片！
* **安全防线铁律**：
  1. 拨动该开关时，必须弹出高危阻断模态弹窗：
     > **【高危警示：就地覆盖原照片】**  
     > 开启此功能将**永久剥离并删除相册内嵌的实况短视频**，原文件将不可逆转换为静态照片。  
     > 若您希望保留实况回放能力，请保持此项关闭，系统将安全导出到新目录。  
     > `[我已知晓风险，继续开启]`  `[取消，推荐安全导出]`
  2. 底层写入时，必须先将原图重命名备份至 `.livephoto_backup/`，新 HEIC 写入并校验完整（文件大小与魔数合规）后方可清理备份，确保断电时原片毫发无损。

---

### 3. 磁盘满溢（ENOSPC）前置预检与孤儿临时目录自愈 (SEC-03)
* **隐患分析**：
  - 海量实况照片转码与流式拼接需占用数倍于单文件的磁盘空间。若目标盘或系统盘剩余空间不足，中途报错 `0x80070070 (ERROR_DISK_FULL)` 会导致半成品残留并锁死系统盘；
  - 若用户在转码中途强杀进程，`try ... finally` 中的清理代码无法执行，系统临时目录会残留大量孤儿文件。
* **安全防线铁律**：
  1. **空间预检（Pre-flight Disk Check）**：点击开始转换前，按公式 $\text{RequiredSpace} = \text{TotalSourceSize} \times 1.2 + 500\text{MB}$ 检查磁盘可用空间，不足时主动阻断并弹窗警告；
  2. **孤儿自愈机制（Startup Orphan Sweep）**：每次客户端启动时，静默清理 `%TEMP%/LivePhotoConvert/` 中超过 24 小时或非当前进程锁定的孤儿临时目录。
